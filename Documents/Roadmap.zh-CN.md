# Roadmap

> [English Version](./Roadmap.md)

本文档用于记录 ZFS Manager 的功能路线图、当前已完成阶段，以及接下来的推荐开发顺序。

## 当前进度

截至目前，以下阶段已经完成或已有可用基础：

- 任务系统基础层
  - 现有写操作已经接入任务记录
  - 已有任务列表和任务详情接口
  - 前端已有独立的任务记录页面
- 任务持久化与恢复
  - 已接入 `SQLite` 持久化
  - 后端重启后会自动加载最近任务历史
  - 已有未完成任务的启动对账能力
- `scrub` 基础能力
  - 已支持手动启动 `scrub`
  - 已支持停止 `scrub`
  - 已在存储池详情中展示 `scrub` 状态、进度、ETA 和相关说明
  - 已支持基于 `zpool status` 的 `scrub` 进度恢复
- 定时工作流基础能力
  - 已有独立的计划任务页面
  - 已支持创建、启用、停用和删除按周定时 `scrub`
  - 定时快照区域已预留占位
- 任务记录页可用性增强
  - 页面名称已调整为“任务记录和状态”
  - 记录改为分页加载，而不是一次性全部载入
  - 已支持按状态筛选
  - 筛选结果为空时不再破坏整个页面框架

## 规划原则

- 延续现有的 `状态采集 + REST 写操作 + 强制刷新` 架构，不额外引入平行状态模型
- 对长时间操作统一走任务系统，而不是让每个功能自行维护进度与状态
- 能力判断尽量由后端输出明确字段，前端只消费结果，不自行推断风险规则
- 优先依赖 ZFS 和系统本身可重新读取的真实状态，其次才是本地任务记录
- 任务记录与恢复系统要按“可扩展”设计，便于后续接入 `scrub`、`replace`、`expansion`、定时快照和审计功能

## 已落地部分

### 1. 任务系统

已完成：

- 统一任务数据模型
- 任务列表与详情接口
- 独立的任务记录页面
- `SQLite` 持久化
- 启动恢复基础框架
- 任务状态对账
- 任务记录分页与状态筛选

当前支持的核心状态：

- `queued`
- `running`
- `succeeded`
- `failed`
- `canceled`
- `recovering`
- `unknown`
- `needs_attention`

### 2. Pool Scrub

已完成：

- 手动启动 `scrub`
- 手动停止 `scrub`
- 在池详情中显示当前扫描状态
- 从 `zpool status` 解析进度、ETA 和完成状态
- 后端重启后恢复 `scrub` 任务状态

### 3. 定时 Scrub

已完成：

- 独立的计划任务页面
- 支持为每个 pool 创建按周执行的 `scrub` 计划
- 支持启用、停用和删除计划
- 计划配置持久化到本地任务数据库
- 计划执行结果继续通过统一任务系统记录

## 下一阶段重点

### 1. 快照管理

目标：

- 快照列表查看
- 手动创建快照
- 删除快照
- 回滚或恢复快照
- 定时快照
- 保留策略和自动清理

当前建议：

- 第一阶段继续放在 `DatasetsView` 内完成
- 等定时快照、保留策略、批量操作明显增加后，再评估是否拆分独立快照页面

### 2. Pool Device Replace

目标：

- 替换候选盘发现
- 替换前资格校验
- 发起 `replace`
- 通过任务系统跟踪 `resilver` 进度

实现要求：

- 后端输出明确能力字段，例如 `canReplace`、`replaceCandidates` 和不可执行原因
- 恢复逻辑优先依赖 `zpool status`

### 3. Single-Disk Expansion

目标：

- 单盘扩容资格判断
- 发起扩容
- 通过任务系统跟踪长时间进度

实现要求：

- 先做只读资格判定，再开放执行入口
- 与 `replace/resilver` 复用一部分恢复与进度跟踪基础设施

### 4. 定时快照与保留策略

目标：

- 补齐计划任务页面中的快照区域
- 持久化快照计划配置
- 增加保留规则和自动清理执行
- 把计划执行结果登记为普通任务记录

### 5. 运维能力补强

建议补充：

- 快照保留与清理报告
- `offline/online` 设备操作
- 运维可见审计历史
- Pool 或磁盘告警
- 更细粒度的权限控制
- 更清晰的失败摘要和操作建议

## 推荐开发顺序

1. 快照基础管理
2. 定时快照与保留策略
3. `replace`
4. `single-disk expansion`
5. `offline/online`、审计、告警等补强能力

## 任务系统后续演进

为了保证扩展性，任务系统建议继续按以下方向演进：

- 增加任务计划表、任务事件表和任务日志表
- 使用可注册的恢复器，而不是把所有恢复逻辑堆在一个文件里
- 区分不同恢复策略：
  - `pool_scan_based`
  - `state_reconcile_based`
  - `scheduler_based`
  - `app_only`
- 支持识别并纳入“不是由当前前端发起，但系统中真实发生了”的外部任务

## 快照界面方向

关于“快照是否应拆成独立页面”，当前仍建议保持分阶段策略。

### 方案 A：先放在 `DatasetsView`

优点：

- 与 dataset/zvol 上下文天然贴合
- 可以复用现有树形选择模型
- 第一版实现成本更低

限制：

- 快照数量大时容易让 dataset 页面变得拥挤
- 计划任务、保留策略和批量操作会越来越难清晰表达

### 方案 B：后续拆分独立快照页面

适合时机：

- 快照数量显著增加
- 定时快照和保留策略成为核心工作流
- 需要跨 dataset 过滤、批量操作或更完整的历史视图

### 当前结论

1. 第一阶段在 `DatasetsView` 中完成快照基础管理
2. 当计划任务、保留策略和批量管理需求增强时，再拆分独立快照页面
